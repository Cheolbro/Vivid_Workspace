#1. 모션 코믹 파이프라인 기능 명세서 (v4.0)
##1.1 시스템 개요 및 목표
- 목표: 20~30분 분량의 심층 대본과 오디오(.mp3), SRT 파일, 그리고 Vrew에서 TTS/자막 편집이 완료된 원본 .vrew 프로젝트 파일을 입력받아, 전문가 캐릭터의 정밀한 립싱크와 역동적인 카메라 워킹이 가미된 '하이엔드 모션 코믹' 영상을 로컬 환경에서 자동 생성합니다.
- 핵심 전략:
(1) 정적인 이미지를 넘어선 **'일러스트 기반 모션 코믹(illustration-based Motion Comic)'**과 공간감을 주는 **'2.5D 패럴랙스(Parallax)'** 기법을 단일 씬 안에서 동시에 구현합니다.
(2) LLM의 코드 생성 오류(Hallucination)를 원천 차단하기 위해 '템플릿 주입(Template Injection)' 방식을 채택합니다.
(3) 장편 렌더링 시 브라우저 메모리 한계를 극복하기 위해 '씬(챕터) 단위 분할 렌더링 및 병합' 아키텍처를 도입합니다.

## 1.2 하드웨어 및 소프트웨어 스택
- 하드웨어 (확정): Intel Core Ultra 5 125H 내장 Intel Arc Graphics, 시스템 공유 VRAM 최대 8.9GB 할당.
가속 엔진: Intel Extension for PyTorch (IPEX) / directml (Intel용).
    * 실행 파라미터: ComfyUI는 환경 변수(GPU_VENDOR=INTEL)를 참조하여 --directml 또는 IPEX 모드로 자동 전환되도록 유동적 래퍼(Wrapper) 스크립트를 구성합니다.

- VRAM 제약 기반 처리 정책 (Mandatory Concurrency Policy):
    * GPU 동종 병렬 금지: VRAM이 매우 제한적인 통합 그래픽 환경이므로, ComfyUI(FLUX.1-schnell) 호출 시 동종 병렬 처리는 절대 금지합니다. n8n 루프는 반드시 순차적(Sequential, Batch size 1)으로 실행되도록 설계하여 OOM(Out of Memory)을 방어하십시오. ComfyUI는 GPU 단일 프로세스 점유 모델이므로 같은 시점에 GPU는 항상 1개의 챕터(또는 1개의 에셋)만 처리.
    * 이종 작업 스마트 파이프라이닝 (Asynchronous Pipelining):
        - 같은 시점에 GPU 1개 + CPU 1개가 서로 다른 챕터를 처리하도록 워크플로우 구성.
        - N 챕터의 모든 Node 7(ComfyUI) 호출이 끝난 직후 Node 11(HyperFrames CPU/Chromium 렌더)을 시작하고, 동시에 N+1 챕터의 Node 7(ComfyUI)을 즉시 디스패치하여 GPU를 유휴로 두지 않음.
        - 즉, GPU는 N+1 챕터 에셋 생성 / CPU는 N 챕터 영상 인코딩을 동시 진행.
    * 효과: 'GPU 에셋 생성'과 'CPU 영상 렌더링'을 교차시켜 대기 시간을 제거하고, 전체 공정에서 최소 1시간 이상 단축합니다.
    * Node 11의 챕터별 동시 렌더링은 본 정책에 따라 비활성화하며, 단일 직렬 + Pipelining 방식만 허용합니다.

- FLUX.1-schnell 모델 운영 정책 (BN-1):
    * 양자화: GGUF Q5_K_M 기본 채택 (VRAM 약 7.5GB, 품질 손실 3~5% 미미). 시스템 OOM 발생 시 Q4_K_M으로 하향 조정.
    * Sampling Steps: 3 step 기본 (4 step 대비 시간 25% 절감, 품질 손실 5~8%로 저널리즘 webtoon 화풍에선 체감 미미). 시간 여유 확보 또는 품질 부족 판단 시 운영자가 4 step으로 상향.

- VRAM 동시 점유 정책 (BN-1 보강 — 8.9GB 한계 방어):
    * 모드별 강제 다운그레이드:
      - Auto 모드 (pose:auto): Q5_K_M(7.5GB) + FaceID(0.5) + IP-Adapter(0.5) + LoRA(0.3) = 8.8GB → 한계 내
      - Controlled 모드 (pose:<id>, ControlNet 활성): **Q4_K_M(6.0GB)으로 자동 다운그레이드 강제** + FaceID(0.5) + IP-Adapter(0.4) + LoRA(0.3) + ControlNet(0.7) = 7.9GB → 한계 내
      - Background/Foreground (Node 7C/7D): IP-Adapter 노드 자체 제거 (이미 명세 반영)
      - Prop with ref_image_id:'none' (Node 7B): IP-Adapter weight=0이면 모델 자체 unload (VRAM 0.5GB 회수)
    * Q4_K_M 다운그레이드 기준: ControlNet 활성 시 자동, 운영자 선택권 없음 (OOM 즉시 방어).
    * 품질 영향: Q4_K_M은 원본 대비 8~13% 손실, 저널리즘 webtoon 화풍에서 미세 디테일(눈썹/천 질감) 정도 무뎌짐 — 시청 체감 거의 없음.
    * ComfyUI 래퍼 스크립트가 페이로드의 pose 필드를 검사하여 모델 로드 분기를 수행 (운영자 수동 개입 0).

- 영상 출력 규격 (MO-6):
    * 해상도 1920×1080 / fps 30 고정 / H.264 코덱.
    * project_config.json baseline에 target_fps:30 명시. 영상별 변동 없음.

- 에셋 인코딩 정책 (BN-2):
    * ComfyUI 출력 PNG → Node 9에서 WebP lossless로 자동 변환. 알파 채널 무손실 보존, 파일 크기 50% 감소, Chromium 디코딩 시간 10% 절감.
    * 디스크 압박 시 단계적 WebP lossy 95%로 전환 가능 (운영자 판단).
    * 챕터 mp4 인코딩은 Intel Quick Sync(h264_qsv) 하드웨어 가속 사용 — 인코딩 시간 50% 절감.

- 가속 오케스트레이션: n8n (비동기 웹훅 트리거, 노드 간 데이터 전달, 루프 제어)
- 에셋 생성: ComfyUI API (FLUX.1-schnell GGUF 양자화 모델)
- 오디오 분석: Rhubarb Lip Sync (음성 파형 기반 입모양 데이터 추출 CLI)
- 배경 제거: ComfyUI LayerDiffusion 또는 FLUX 환경에 최적화된 BRIA RMBG 노드
- 렌더링 및 병합: HyperFrames (HTML/CSS/GSAP) 및 FFmpeg

##1.3 n8n 기반 장편 최적화 자동화 워크플로우
###Step 1: 데이터 로드 및 정밀 기획 (Chunking & Planning)

### [Node 1] Load Files: 데이터 로드 및 챕터 청킹 (구조적 노드)
#### 목표: 30분 장편 영상을 안정적으로 처리하기 위해 데이터를 쪼개는 진입점입니다. 프롬프트는 없지만, 자바스크립트/파이썬 코드로 아래 로직이 반드시 구현되어야 합니다.
#### 동작 로직:
(1) 태그 기반 청킹 (tag-based Chunking) — MO-7 보정
- 원본 script.txt를 분석하여 [INTRO], [BUMPER], [CHAPTER_N] 마크다운 태그에 따라 메타데이터로 작성한다.
* 사용 태그: [INTRO] / [BUMPER] / [CHAPTER1], [CHAPTER2], ... [CHAPTERN]
* OUTRO는 별도 청크로 분리하지 않으며, 마지막 [CHAPTERN]이 OUTRO 역할을 겸한다 (일반 챕터처럼 동적 렌더).
* Node 1은 대본을 읽을 때 [BUMPER] 태그가 발견되면, 해당 지점에 **type: "BUMPER_TRIGGER"**를 가진 빈 아이템을 생성하여 데이터 배열(Array)에 포함합니다.

(2) 구조적 데이터 생성 (Structural Data Array) — CL-1 보정
- 분할된 각 챕터마다 다음 chapter_meta 객체를 생성합니다:
  * chapter_id (예: "chapter_01")
  * type ("INTRO" | "BUMPER_TRIGGER" | "CHAPTER" — 마지막 챕터도 "CHAPTER")
  * chapter_global_start: 원본 mp3/SRT 기준 글로벌 시작 초
  * chapter_global_end: 원본 mp3/SRT 기준 글로벌 종료 초
  * duration_sec: chapter_global_end - chapter_global_start
  * script_text: 해당 챕터 대본
  * srt_path: 챕터 내부 0초 기준으로 재계산된 SRT 파일 경로
- 글로벌 타임코드는 Node 1.2(mp3 분할), Node 13(Vrew clip 매칭)에서 사용. Node 2~11은 챕터 내부 0초 기준 그대로 동작.

(3) 분할된 챕터 수만큼 n8n 워크플로우 아이템(Items)을 생성하여 다음 노드로 흘려보냅니다.

(4) 원본 .vrew 파일 경로 보존 (Vrew Source Passthrough)
- 입력으로 받은 원본 .vrew 파일의 경로를 워크플로우 전역 데이터로 저장하여, 최종 단계(Node 13)에서 참조할 수 있도록 합니다.

(5) 챕터 내부 0초 기준 시간 좌표계 강제 (Chapter-relative Timecode)
- 청킹된 각 챕터의 시작 시간은 항상 00:00:00으로 리셋되어 다음 노드로 전달됩니다.
- SRT 데이터도 챕터 내부 0초 기준으로 재계산하여 chapter_NN_subtitle.srt로 저장합니다.
- 이후 Node 2 (Rhubarb), Node 3 (연출 기획), Node 10 (Master Assembler), Node 11 (HyperFrames 렌더)은 모두 챕터 내부 0초 기준 타임코드로 동작합니다.
- 글로벌 영상 타임라인은 Node 12 (FFmpeg Concat) 단계에서만 챕터 순서에 따라 자연 형성됩니다.

### [Node 1.1] Bumper 분기 노드 — MO-7 보정
- type === "BUMPER_TRIGGER"인 아이템은 Node 2~10을 건너뛰고 곧바로 Node 12의 FFmpeg Concat 리스트에 bumper.mp4 경로만 삽입합니다.
* 루트 폴더의 \shared_assets\bumper.mp4를 참조
- type === "INTRO" | "CHAPTER" 아이템은 Node 1.2로 전달됩니다.
- OUTRO_TRIGGER는 폐기되었으며, 마지막 [CHAPTERN]이 일반 CHAPTER로서 동적 렌더됩니다.

### [Node 1.2] FFmpeg Audio Splitter: 챕터별 오디오 분할 (CLI 제어 노드)
#### 목표: Node 2의 Rhubarb가 '챕터 내부 0초'를 기준으로 립싱크 데이터를 정확히 추출할 수 있도록, 원본 통합 mp3를 챕터 단위로 물리적으로 분할합니다. (최종 결과물 Vrew에서는 비디오만 사용되지만, Rhubarb 분석을 위해 챕터별로 잘린 오디오 조각이 반드시 필요합니다.)
#### 동작 로직:
(1) FFmpeg 무손실 분할 (Lossless Split)
- n8n의 Execute Command 노드가 원본 mp3와 Node 1에서 산출된 챕터별 글로벌 시작/종료 타임코드를 입력받아 FFmpeg를 호출합니다.
- 명령어 예시: ffmpeg -ss {chapter_global_start} -to {chapter_global_end} -i {original.mp3} -c copy -y project/audio/chapter_NN.mp3
- 인코딩 손실을 방지하기 위해 -c copy(스트림 카피) 모드를 강제합니다.

(2) 챕터별 오디오 경로 주입 (Audio Path Injection)
- 분할된 chapter_NN.mp3의 절대 경로를 각 챕터 아이템의 chapter_audio_path 필드에 주입하여 Node 2로 전달합니다.

(3) 오류 방어 (Error Handling)
- FFmpeg 분할 실패 시 최대 3회 자동 재시도하고, 최종 실패 시 Error Trigger를 활성화하여 관리자(Telegram)에게 에러 로그를 즉시 전송하고 작업을 일시정지합니다.
- 결과 파일이 0바이트이거나 duration이 의도한 값과 ±0.5초 이상 차이날 경우 실패로 간주합니다.

(4) 분할 범위 정책 (MO-1)
- 본 파이프라인은 챕터 단위까지만 mp3를 물리 분할합니다. 씬 단위 mp3는 만들지 않습니다.
- HyperFrames(Node 11)는 챕터 영상을 무음으로 렌더하고, 최종 영상의 음원은 Vrew(Node 13) 단계에서 원본 TTS 트랙이 담당합니다.
- 따라서 Node 2 Rhubarb는 챕터 mp3 단위로만 lipsync를 분석하고, Node 10이 lipsync cue를 씬 범위로 필터링하여 분배합니다.

### [Node 2] Audio Analyst: 립싱크 데이터 추출 (CLI 제어 노드)
#### 목표: 캐릭터의 입이 언제 움직이고 언제 멈춰야 할지 물리적인 근거 데이터를 생성합니다.
#### 동작 로직:
(1) Rhubarb 백그라운드 실행 : n8n의 Execute Command 기능을 사용해 각 챕터의 오디오 파일을 처리합니다.
* 실행 명령어: rhubarb {chapter_audio.mp3} -f json -o {output_lipsync.json}

(2) Speaking 구간 데이터 정제 (Voice Extraction)
- 반환된 JSON 데이터 중 수많은 입모양 알파벳(A~F, X) 중에서, 입이 움직이는 구간인 'A~F(또는 통칭 Speaking 구간)'의 시작/종료 타임코드를 추출하여 배열로 묶어 저장합니다. 이 배열은 최종 렌더링 노드에서 입술 깜빡임(Toggle) 및 하관이 들썩이는 턱관절 바운스(Scale Bounce) 애니메이션을 활성화(active)시키는 절대적인 트리거가 됩니다.

(3) 립싱크 데이터 물리적 저장 (Persistent Storage)
- 정제된 Speaking 구간 배열을 project/lipsync/chapter_NN_lipsync.json 파일로 
  로컬 디스크에 저장합니다. 
- 이 파일은 Node 10(Master Assembler)이 3원 병합 시 직접 읽어오며, 
  파이프라인 중단 후 재실행 시에도 Rhubarb를 다시 돌리지 않아도 되는 
  캐시 역할을 합니다.

(4) 자동 재시도 (Retry Strategy)
- Rhubarb 분석 실패 시, 전체 파이프라인을 중단하지 않고 해당 노드만 최대 3회 자동 재시도하도록 n8n 설정을 강제합니다

(5) Error 발생시 조치사항
- 3회 재시도 후에도 Rhubarb 분석에 실패할 경우, Error Trigger 노드를 활성화하여 관리자의 텔레그램으로 에러메세지를 전송한 후 작업을 일시정지하고 대기합니다.

(6) 병렬 실행 정책 (BN-4)
- Rhubarb는 CPU만 사용하므로 GPU 작업과 완전 병렬 가능.
- n8n 워크플로우에서 Node 2를 Node 3·4·7과 동일 시점에 디스패치 가능 (분기 후 합류).
- 병렬 실행으로 Rhubarb 분석 시간(챕터 10개 × 30~60초 = 5~10분)을 GPU 작업 시간 안에 흡수하여 실질 추가 시간 0.

### [Node 3] Run Analysts: 총괄 연출 기획 (Gemini 프롬프트)
#### 목표: 대본을 분석하여 2.5D 카메라의 안무, 다이내믹한 캐릭터 컷/포즈, 화면 이펙트를 유연하게 통제하는 '감독'의 뇌를 세팅합니다.

#### 동작 로직: 
- Gemini Cli를 호출하여, 분할된 대본 텍스트와 SRT 타임코드를 입력하고, 미리 정의된 엄격한 JSON 스키마에 맞춰 연출 기획안을 반환하도록 강제합니다.

**필수 로직 : 최종 JSON 스키마 강제**
- 반드시 지정된 JSON 스키마 형식으로만 출력하십시오.  
- 씬 번호를 키(Key)값으로 하여 다음 필드만 포함된 JSON만 반환하십시오: character_pose, camera_choreography (줌 배율 포함), kinetic_typography, scene_context, vfx_active, structure_logic, ambient_effect, scene_transition, characters(배열). 

**연출 기획안 물리적 저장 (Persistent Storage)**
- 생성된 연출 기획 JSON을 project/plan/chapter_NN_plan.json 파일로 
  로컬 디스크에 저장합니다.
- 파이프라인 중단 후 재실행 시 Gemini를 다시 호출하지 않아도 되는 
  캐시 역할을 합니다.

**오류 방어 로직 (Error Handling)**

- 최종 실패 시 Error Trigger를 활성화하여 관리자(Telegram)에게

#### 필수 반영 프롬프트 속성:

- 필수 속성 1: 맥락 맞춤형 캐릭터 컷/포즈 기획 (Dynamic Character Pose)
"대본의 맥락을 분석하여 씬마다 캐릭터가 취할 역동적인 전체 포즈와 화면 구도를 기획하세요. 부분적인 표정 스위칭이 아니라, '책상을 내리치며 분노하는 상반신 컷', '뒷짐을 지고 걸어가는 전신 컷'처럼 상황에 맞는 통짜 캐릭터 일러스트 생성을 위한 구체적인 묘사를 JSON(character_pose)으로 지정하십시오."

- 필수 속성 2: 다이나믹 2.5D 카메라 안무 (camera choreography)
"화면 전체를 담는 .scene 컨테이너의 움직임을 설계하세요. 대본의 흐름에 따라 시청자의 시선이 닿아야 할 곳으로 카메라의 좌표(x, y)와 배율(scale)을 수치화하여 지시하십시오.(JSON Key: camera_choreography 사용) (예: 핵심 정보 등장 시 x:-100, y:50으로 scale 1.2배 줌인)"

- 필수 속성 3: 맥락 맞춤형 타이포그래피 (contextual kinetic target)
"시력 보완이 필요한 주 시청자층을 위해, 대본 전체를 자막으로 띄우지 마십시오. 화면에 거대하게 팝업시킬 10자 이내의 단기 임팩트 명사구만 1~2개 추출하세요. 또한 해당 단어의 무게감에 맞춰 등장 Easing 모션(무거우면 bounce, 날카로우면 slide 등)을 다르게 지정하십시오.(JSON Key: kinetic_typography 사용)"

  - 정밀 타이밍 규칙 (Precise Timing Rule):
    * 출력 스키마에 반드시 appear_time(초)과 duration(초) 필드를 포함합니다.
    * appear_time은 SRT 데이터상 해당 키워드가 발화되는 시점(챕터 내부 0초 기준)과 일치시킵니다.
    * 정보의 충분한 인지를 위해 텍스트는 씬이 종료되기 최소 2초 전에는 화면에 완전히 노출되어야 하며, duration은 씬이 끝날 때까지 텍스트가 화면에 머물도록 산정합니다.
    * 즉, appear_time + duration ≥ scene.end_time 이며, appear_time ≤ scene.end_time - 2.0 을 만족해야 합니다.
    * 출력 예시: "kinetic_typography": { "text": "골든크로스", "easing": "bounce", "appear_time": 4.5, "duration": 6.5 }

- 필수 속성 3-1: 씬 분할 규칙 (Scene Segmentation Rule) — MO-2 보정
"씬 분할의 절대 규칙(Hard Rule)은 '문장 단위'입니다. 대본(.txt)의 마침표(.), 느낌표(!), 물음표(?)로 종결되는 문장 경계를 절대 침범할 수 없습니다. 한 씬은 반드시 1개 이상의 완전한 문장으로 구성되며, 한 문장의 일부만 따로 떼어 다른 씬에 배치하는 것은 금지됩니다.
보조 가이드(Soft Rule)는 씬 duration 8~15초입니다. 가급적 이 범위 안에서 씬을 구성하되, 다음 우선순위로 처리하십시오:
  1. 한 문장이 너무 짧아 단독으로 8초 미만이면 → 다음 문장과 합쳐 한 씬으로 구성 (12~15초 권장).
  2. 한 문장이 너무 길어 단독으로 15초를 초과하면 → 그 문장 단독으로 한 씬을 구성 (15초 초과 허용).
  3. 단순 전환·짧은 대화 문장 묶음 → 8~10초.
  4. 깊은 설명·정보량 많은 문장 묶음 → 12~15초.
JSON Key: scene.start_time, scene.end_time — 챕터 내부 0초 기준."

- 필수 속성 3-2: 챕터당 씬 개수 가이드 (MO-2 보조)
"챕터 평균 길이 약 3분 기준으로 씬 12~22개를 권장합니다. 8개 미만이면 너무 단조롭고, 25개 초과면 GPU 부하가 과중해집니다. 위 문장 단위 절대 규칙과 충돌 시 절대 규칙이 우선합니다."

- 필수 속성 4: 전략적 조명 및 이펙트 통제 (strategic VFX Control)
"조명과 이펙트를 남발하지 마십시오. 시선을 강제 집중시켜야 하는 특별한 맥락에서만 비네팅(Vignette) 강도를 높이고, 위험/경고 대목에서만 붉은색 점멸(Flicker) 효과를 활성화하도록 vfx_active: true/false 형태로 전략적 판단을 내리십시오.(JSON Key: vfx_active 사용)"

- 필수 속성 5: 영상 구조의 논리적 배치 (structure logic)
"기획되는 모든 연출 타임라인은 영상의 필수 흐름인 '인트로 -> 범퍼 비디오(본문 진입 전 브릿지) -> 본문 -> 아웃트로'의 순서를 정확히 따르도록 배열을 구성해야 합니다. 현재 처리 중인 데이터가 전체 영상 중 어느 위치(인트로/범퍼/본문/아웃트로)에 해당하는지 메타데이터를 참고하여, 그에 맞는 structure_logic 값을 부여하십시오 (JSON Key: structure_logic 사용)"

- 필수 속성 6: 씬 컨텍스트 요약 (scene context)
"대본의 배경과 공간적 분위기를 묘사하는 정보를 추출하십시오.(JSON Key: scene_context 사용)"

- 필수 속성 7: 환경 이펙트 기획 (Ambient Effect Planning)
"씬의 분위기와 맥락에 따라 화면 위에 겹쳐질 환경 효과를 지정하십시오. 사용 가능한 효과: 'rain', 'dust', 'light_rays', 'smoke', 'snow', 'none'. 환경 효과가 필요하지 않은 씬에는 반드시 'none'을 지정하십시오. 과도한 사용은 금지합니다. 효과 유형과 함께 강도(intensity: 'light'/'medium'/'heavy')와 바람 방향(wind_angle: 0~45도)를 맥락에 맞게 지정하십시오. (JSON Key: ambient_effect 사용, 객체 형태. 예: {type:'rain', intensity:'heavy', wind_angle:30})"

- 필수 속성 8: 씬 전환 효과 기획 (Scene Transition Planning)
"각 씬이 시작/종료될 때 적용할 전환 효과를 지정하십시오. 사용 가능한 효과: 'fade_black', 'glitch', 'zoom_blur', 'slide_left', 'cut'(즉시 전환). 대부분의 씬 전환은 'cut'으로 처리하되, 챕터 전환이나 감정 변화가 큰 지점에서만 시각적 전환을 사용하십시오. (JSON Key: scene_transition 사용)"

- 필수 속성 9: 다중 캐릭터 배치 기획 (Multi-Character Staging)
"한 씬에 2인 이상의 캐릭터가 등장하는 경우, 각 캐릭터의 포즈, 화면 내 위치(position: left/center/right), z-index(전면/후면)를 개별적으로 기획하십시오. characters 배열에 각 캐릭터 객체를 독립적으로 포함시킵니다. (JSON Key: characters 사용, 배열 형태)"


### [Node 4] Asset Prompt Engineer: 캐릭터/소품/배경 프롬프트 (Gemini 프롬프트)
#### 목표: 앞선 연출 기획안(Node 3)을 바탕으로, ComfyUI(FLUX)가 렌더링해야 할 '통짜 캐릭터', '무대(배경)', '소품'의 영문 프롬프트를 각각 분리하여 추출합니다(JSON Key: asset_prompts 사용).
#### 동작 로직 : 
- Gemini Cli를 호출하여, 3번 노드의 scene_context와 대본, 그리고 references_catalog.json을 바탕으로 실제로 렌더링해야 할 에셋의 영문 프롬프트만 분리해서 추출하고 asset_prompts 로 반환합니다.
- 오류 방어 로직 (Error Handling)
  - Gemini CLI 호출 실패, 응답 거부, 또는 반환값이 유효한 JSON이 아닐 경우 
    최대 3회 자동 재시도합니다.
  - 최종 실패 시 Error Trigger를 활성화하여 관리자(Telegram)에게 
    에러 로그를 즉시 전송하고 작업을 일시정지합니다.
#### 필수 반영 프롬프트 속성:

- 필수 속성 1: 일관성 있는 캐릭터 프롬프트 생성 (Consistent Character Generation)
"Node 3에서 기획된 character_pose(예: 책상을 내리치는 포즈)를 바탕으로 역동적인 캐릭터 일러스트 프롬프트를 작성하십시오. 단, 씬이 바뀌어도 인물의 정체성이 유지되도록 프롬프트 앞단에 지정된 외모 묘사(예: 'A 30-something Korean man, wearing a neat dark suit, glasses')를 반드시 고정값으로 포함시켜야 합니다."

- 필수 속성 2: 배경 및 소품 분할 생성과 메타데이터(Type) 강제 지정 (Asset Type Tagging)
"대본 맥락에 맞춰 바뀌어야 하는 Background와 Props에 대한 프롬프트도 캐릭터 프롬프트와 함께 배열(Array) 형태로 출력하십시오. 이때 가장 중요한 것은 각 프롬프트 객체에 반드시 asset_type 키를 포함하는 것입니다. 그 값은 프롬프트의 성격에 따라 'character', 'prop', 'background', 'foreground' 4가지 중 하나로만 정확히 지정하십시오. 이 메타데이터는 후속 파이프라인에서 투명화(누끼) 적용 여부를 결정하는 절대적인 스위치로 사용됩니다."

- 필수 속성 3: 네이티브 투명화를 위한 형태 통제 (Alpha-Ready Isolation - 조건부 적용)
"당신이 asset_type을 'character' 또는 'prop'으로 지정한 객체의 프롬프트에는 반드시 'isolated single object, centered, perfect composition for transparent PNG' 지시어를 포함하십시오. 반대로 asset_type을 'background'로 지정한 객체에는 이 지시어를 절대 넣지 마십시오."

- 필수 속성 4: 저널리즘 화풍 앵커 (Journalistic Style Anchor)
"과장된 만화적 밈(Meme) 스타일을 절대 피하고, 언론사 채널의 전문성을 유지하십시오. 모든 프롬프트의 끝에는 **informative webtoon style, noir economic illustration, bold clean vector lines**라는 화풍 지시어를 앵커(Anchor)로 강제 부착하여 출력하십시오."

- 필수 속성 5: 레퍼런스 이미지 ID 매핑 (Reference ID Mapping) — MO-4 보정
캐릭터 및 소품 프롬프트 생성 시, references_catalog.json의 5계층 검색을 반드시 다음 순서로 명시 시도합니다:
  1. characters (match_score ≥ 0.7, FaceID 강제)
  2. static_assets (정확 ID 매칭, 임베딩 검색 X)
  3. auto_generated_assets (코사인 유사도 ≥ 0.85, hnswlib 검색)
  4. props (match_score ≥ 0.7, img2img용)
  5. 1~4 모두 미스 → ref_image_id: "none"으로 폴백 + generate_asset: true 마킹

Node 4는 출력에 search_log 필드를 포함하여 시도한 카테고리와 매칭 결과(category, asset_id, score)를 명시 기록해야 합니다. 이 로그가 없거나 5계층 시도가 누락된 출력은 즉시 재시도 처리합니다.

캐릭터/소품 매칭 시 scene_asset_id(예: character_01, prop_01)를 챕터 내 등장 순서에 따라 별도로 부여하십시오. ref_image_id와 scene_asset_id는 독립적으로 관리됩니다.

ref_image_id 매핑 예시:
* 정면 대화 씬 ➡️ char_[ID]_front_neutral
* 걷거나 이동하는 씬 ➡️ char_[ID]_side_left 또는 _side_right
* 뒷모습이 강조되는 씬 ➡️ char_[ID]_back
* 특정 소품 등장 ➡️ prop_[ID] 등

- 필수 속성 5-1: pose 라이브러리 매칭 (MO-3, v4.5 §4.2)
"Node 3의 character_pose(자연어 묘사)는 그대로 ComfyUI 프롬프트 본문에 포함시키십시오. 동시에 pose_library.json을 검색하여 가장 유사한 pose_id가 있으면 pose 필드에 매칭, 없으면 pose:'auto'로 출력합니다.
두 필드는 공존 가능하며 다음과 같이 작용합니다:
  * pose:'auto' → character_pose 자연어가 단독으로 ComfyUI 프롬프트에 영향. ControlNet 비활성. (LLM 창의 80%)
  * pose:'<pose_id>' → ControlNet OpenPose가 우선, character_pose는 보조 묘사로 프롬프트에 포함. IP-Adapter weight 0.30~0.40. (시스템 통제 20%)
이로써 LLM 창의성과 시스템 통제력이 충돌 없이 공존합니다."

- 필수 속성 5-2: 출력 시드 정책 (EF-1 보정)
"동일 인물·소품의 영상 1편 내 캐시 재사용을 위해, seed를 다음 단위로 결정합니다:
  * 캐릭터(asset_type: 'character'): SHA1(video_id + ref_image_id)의 32-bit 해시 — 한 영상 내 같은 인물은 항상 동일 시드 → L3 캐시 히트율 극대화.
  * 소품(asset_type: 'prop'): SHA1(video_id + ref_image_id)의 32-bit 해시 — 같은 소품 재등장 시 캐시 히트.
  * 배경(asset_type: 'background') / 전경(asset_type: 'foreground'): 씬 단위 시드(scene_id 기반). 화풍 일관성을 위한 기존 정책 유지.
이 정책으로 캐릭터·소품의 ComfyUI 호출이 영상 1편 내 30~50% 감소 예상."

- 필수 속성 6: 전경 레이어 프롬프트 (Foreground Layer Prompt)
"대본의 공간적 맥락에 따라, 카메라와 캐릭터 사이에 위치하는 전경 오브젝트(난간, 창문 프레임, 나뭇가지, 철조망 등)의 프롬프트를 생성하십시오. asset_type을 반드시 'foreground'로 지정하고, 투명 PNG 규격을 따릅니다. 전경 레이어는 2.5D 패럴랙스에서 가장 빠른 이동 속도(scale 1.25)를 가지며 깊이감을 극대화합니다. 모든 씬에 필수는 아니며, 공간감이 필요한 씬에서만 선택적으로 사용하십시오."

- 필수 속성 7: 다중 캐릭터 프롬프트 (Multi-Character Prompt)
"Node 3의 characters 배열에 2인 이상의 캐릭터가 기획된 경우, 각 캐릭터마다 독립된 프롬프트 객체를 생성하십시오. 각 프롬프트에는 scene_asset_id(예: character_01, character_02)와 화면 내 배치 위치(position: left/center/right)를 반드시 포함합니다."


### [Node 5] Item Lists: 에셋 프롬프트 배열 분할 (Split Out)
#### 목표: 앞선 기획 노드에서 배열(Array) 형태로 한 번에 묶여서 추출된 여러 개의 프롬프트를 개별 아이템(Items)으로 쪼개어, 이후 API 호출 시 병목이 발생하지 않도록 작업을 분배합니다(LLM 프롬프트 없음).
#### 동작 로직:
- 필수 로직 1: 1대 다(1-to-N) 데이터 전개
Node 4의 출력 결과는 보통 1개의 n8n 아이템 안에 prompts: [ {캐릭터}, {배경}, {소품} ] 처럼 배열로 담겨 있습니다. Item Lists 노드가 이 배열을 읽고 Field To Split 설정(asset_prompts 등)을 통해 분해하여, n8n의 작업 단위를 1개에서 3개의 독립된 아이템으로 증식시킵니다.
(Include Other Fields 옵션을 켜서 씬 번호 등의 메타데이터를 유지해야 합니다.)

- 필수 로직 2: 후속 노드의 순차/병렬 처리 활성화
이 노드를 거쳐 아이템이 여러 개로 나뉘면, 바로 뒤에 붙는 [Node 6] ComfyUI API 호출 노드는 사용자가 루프 코드를 짜지 않아도 분할된 아이템의 개수만큼 자동으로 반복 실행(Iteration)되게 됩니다.

- 필수 로직 3: 챕터 단위 분할 강제 (EF-2 보정 — Sub-workflow 분리 정책)
- 본 노드(Node 5)는 단일 챕터 인스턴스 내에서만 Split을 수행합니다. 즉, 한 인스턴스가 800개+ 아이템을 동시 보유하지 않도록 워크플로우 단위를 챕터로 한정.
- 챕터 N+1의 처리는 Node 5 자체에서 직렬로 가는 게 아니라, **상위 워크플로우(Master Workflow)가 챕터별 Sub-workflow 인스턴스를 별도 트리거**하여 진행합니다.
  * Master Workflow 책임: Node 1·1.1·1.2 수행 후, 챕터별로 Sub-workflow(`pipeline_chapter`)를 비동기 디스패치
  * Sub-workflow 책임: Node 2 ~ Node 11(또는 Node 9)까지 단일 챕터 처리. n8n 메모리는 항상 1개 챕터 분량만 보유.
  * Master Workflow는 Sub-workflow 큐를 모니터링하여 GPU 큐(Node 7)와 CPU 큐(Node 11)가 서로 다른 챕터에서 동시 실행되도록 디스패치 타이밍 조정.
- 이 정책으로 §1.2의 이종 파이프라이닝(GPU N+1 챕터 + CPU N 챕터 동시 진행)이 실제 구현 가능해집니다.
- 단일 워크플로우 내 챕터 직렬 강제는 폐기 (Sub-workflow 인스턴스 분리로 대체).


##Step 2: 로컬 에셋 자동 생성 및 상태 관리 (Generation & Polling)
이 단계는 n8n이 로컬 GPU 자원을 점유하고 있는 ComfyUI에게 작업 지시를 내리고, 결과가 나올 때까지 안전하게 기다리는 과정입니다.

### [Node 6] Switch: 에셋 타입별 렌더링 분기 (분기 제어 노드) - 신규 추가
#### 목표: 투명화가 필요한 피사체와, 투명화가 되면 안 되는 배경을 완벽하게 분리하여 각기 다른 렌더링 파이프라인을 타게 만듭니다. (LLM 프롬프트 없음)
#### 동작 로직: 메타데이터 기반 라우팅 (Data-Driven Routing), Node 5에서 넘어온 아이템의 JSON 속성 중 asset_type의 String 값을 검사합니다.
* Route 0 (Output 1): {{ $json.asset_type }} 값이 'character'인 경우 ➡️ Node 7A로 연결
* Route 1 (Output 2): {{ $json.asset_type }} 값이 'prop'인 경우 ➡️ Node 7B로 연결
* Route 2 (Output 3): {{ $json.asset_type }} 값이 'background'인 경우 ➡️ Node 7C로 연결
* Route 3 (Output 4): {{ $json.asset_type }} 값이 'foreground'인 경우 ➡️ Node 7D로 연결


### [Node 7] HTTP Request: ComfyUI API 렌더링 페이로드 (API 제어 노드)
####목표: 로컬에 구축된 FLUX.1-schnell 모델을 호출하여 Node 4에서 설계된 프롬프트를 실제 고퀄리티 이미지로 시각화합니다. 특히 캐릭터와 소품은 이후 레이어 합성을 위해 반드시 배경이 제거된 투명 PNG 상태로 출력하며, 메인 캐릭터의 일관성과 새로운 자산의 창의성을 동시에 확보합니다.  

##### 운영 로직 (Operational Logic)
(0) 3계층 캐시 재사용 정책 — VRAM 보호 최우선 로직 (v4.5 §4.3.4):
- L1 (reuse_asset_id 명시, Node 4 단계): Node 4 출력에 reuse_asset_id가 있으면 Node 7/8을 완전 스킵하고 카탈로그의 PNG 경로를 그대로 Node 9로 전달.
- L2 (임베딩 검색, Node 4 단계): Node 4가 description_search 임베딩 + hnswlib 코사인 유사도 ≥ 0.85 매칭 시 reuse_asset_id로 출력 → L1 경로로 합류.
- L3 (SHA1 캐시, Node 7 단계): L1·L2 모두 미적용 시, ComfyUI API 호출 직전 다음 키로 project/asset_cache/ 검색.

- L3 캐시 키 정책 (EF-1 보정):
  * 캐릭터/소품(asset_type: 'character' | 'prop'): SHA1(ref_image_id + "|" + prompt + "|" + lora_signature)
    - seed는 키에서 제외 — Node 4 필수 속성 5-2의 정책에 따라 동일 인물·소품은 영상 1편 내 동일 시드라 자연스럽게 캐시 일관.
  * 배경/전경(asset_type: 'background' | 'foreground'): SHA1(ref_image_id + "|" + seed + "|" + prompt + "|" + lora_signature)
    - 배경은 씬마다 다른 시드 정책 유지 (화풍 일관성 우선).
- 캐시 히트 시: ComfyUI API 호출을 즉시 건너뛰고, 캐시 파일 경로를 반환하여 Node 9로 직행합니다 (Node 8 웹훅 대기도 스킵).
- 캐시 미스 시: 아래 (1)~(3) 로직 정상 실행 후 결과 PNG를 asset_cache/{hash}.webp(WebP lossless)로 저장.
- 본 캐싱은 Intel Arc 8.9GB VRAM 환경의 렌더링 부하 최소화를 위한 최우선 과제이며, 모든 4개 분기(7A/7B/7C/7D)에 공통 적용됩니다.

(0-1) 사용량 통계 갱신 (EF-7):
- L1·L2·L3 캐시 히트 시 references_catalog.json의 해당 항목 usage_count++ (File Lock 보호).
- 신규 ComfyUI 호출 후 Node 9.5에서 등재된 항목은 usage_count: 0으로 시작.

(1) 하이브리드 분기 실행 (Hybrid Logic):
- Node 4에서 넘어온 ref_image_id가 실제 로컬 /assets/references/ 폴더 내에 존재하는지 n8n의 'File Exists' 또는 'IF' 노드로 1차 확인합니다.
* 파일 존재 시 (메인 캐릭터/소품): LoadImage 노드에 해당 경로를 주입하고 FaceID/IP-Adapter를 활성화하여 일관성을 강제합니다.
* 파일 부재 시 (신규/엑스트라): ComfyUI 내에서 FaceID 및 IP-Adapter 노드를 Bypass(우회) 처리하고, 오직 텍스트 프롬프트 기반의 Pure Text-to-Image 방식으로 생성합니다.

(2) 비동기 웹훅 세션 관리 (Session Management):   
- ComfyUI 워크플로우 마지막의 'HTTP Request' 노드가 n8n의 웹훅 주소(http://n8n-주소/webhook-waiting)를 호출하도록 설정합니다.  
- prompt_id 생성: n8n이 ComfyUI API를 호출할 때, 고유한 UUID를 자동 생성하여 요청 페이로드의 client_id로 사용하고, 이 값을 prompt_id로 다음 노드에 전달합니다.
- 데이터 본문(Body)에 반드시 {"resumeKey": "{{ $json.prompt_id }}"}를 포함하여 전송함으로써, Node 8에서 정확한 세션 복구가 가능하게 합니다.  

(3) 오류 방어 및 플랜 B (Error Handling)
- 자동 재시도 (Retry): 호출 실패 또는 타임아웃 발생 시 파이프라인을 멈추지 않고 해당 노드만 최대 3회 자동 재시도합니다.  
- 최종 실패 시 Plan B (Dummy Video):   
* 3회 재시도 후에도 생성이 불가능할 경우, Error Trigger를 활성화하여 관리자(Telegram)에게 에러 로그를 즉시 전송합니다.  
* 동시에 시스템은 "렌더링 오류 구간 - 수동 수정 필요"라는 자막이 포함된 3초 분량의 검은색 더미 영상 데이터를 생성하여 해당 칸을 채우고, 전체 파이프라인이 멈추지 않고 완주하도록 조치합니다.

#### 에셋 타입별 상세 명세:
- Node 7A (Character 전용): 투명도 생성 워크플로우 (text2img + FaceID + Alpha Channel)
* 목표: 캐릭터의 외모 일관성을 유지하면서 배경이 제거된 투명 PNG를 생성합니다. 
* 필수 파라미터: client_id(n8n 세션 식별 ID), prompt(JSON 데이터). 
* 워크플로우 구조: LayerDiffusion 또는 BRIA RMBG 노드를 KSampler와 SaveImage 노드 사이에 연결합니다. FaceID(IPAdapter), 전용 캐릭터 LoRA, 그리고 Node 4에서 결정된 ref_image_id를 LoadImage 노드에 반드시 포함합니다. 
* 가중치 제어: 얼굴의 일관성을 위해 0.8 이상의 높은 가중치를 적용하고, 스타일 및 복장은 구도 변화를 허용하기 위해 0.6~0.7 수준의 가중치를 적용하여 프롬프트와 레퍼런스의 균형을 맞춥니다. 

- Node 7B (Prop 전용): 실루엣 유지 및 투명도 생성 워크플로우 (img2img + Silhouette Consistency + Alpha Channel)
* 목표: 소품의 원본 형태를 최대한 유지하며 배경이 제거된 투명 PNG를 생성합니다. 
* 필수 파라미터: client_id, prompt. 
* 워크플로우 구조: 캐릭터 노드와 동일하게 투명도 생성 노드를 배치하되, VAEEncode 기반의 img2img 구조를 활성화합니다. Node 4에서 결정된 ref_image_id를 LoadImage 노드에 포함하여 소품의 실루엣 일관성을 강제합니다. 
* ref_image_id가 "none"인 소품은 img2img 대신 text2img 모드로 전환하여 순수 프롬프트 기반으로 생성합니다.
* 설정값: Denoising Strength를 0.5로 지정하여 원본 형태를 보존합니다. 

- Node 7C (Background 전용): 퓨어 배경 워크플로우 (Standard 16:9 + No Alpha)
* 목표: 배경 누끼 처리 없이 16:9 비율의 온전한 배경 이미지를 생성합니다. 
* 필수 파라미터: client_id, prompt. 
* 워크플로우 구조: 투명화 관련 매팅(Matting) 노드 및 인물 고정용 IPAdapter 노드를 완전히 제거한 순수 FLUX 워크플로우를 실행합니다. 

- Node 7D (Foreground 전용): 전경 레이어 투명도 생성 워크플로우 (text2img + Alpha Channel)
* 목표: 카메라와 피사체 사이에 위치할 전경 오브젝트를 배경 제거된 투명 PNG로 생성합니다.
* 필수 파라미터: client_id, prompt.
* 워크플로우 구조: Node 7B(Prop)와 동일한 투명도 생성 파이프라인을 사용합니다. FaceID/IP-Adapter는 비활성화하며 순수 text2img 모드로 작동합니다.
* 패럴랙스 메타데이터: 생성된 전경 이미지에 zoom_rate: 1.25 메타데이터를 부여하여, template.html의 패럴랙스 엔진이 가장 빠른 속도로 이동시키도록 합니다.

- 공통 필수 속성 (Common Attributes):
* 스타일 일관성용 시드 고정 (Contextual Seed Locking): 하나의 씬(Scene) 내 에셋들이 서로 다른 화풍을 가지지 않도록 Node 7A, 7B, 7C, 7D 페이로드 모두 동일한 Seed 값을 공유하도록 세팅합니다. 
* LoRA 가중치 주입: 'Noir/Webtoon Style LoRA' 가중치(0.6 ~ 0.85)를 모든 페이로드에 동일하게 전송하여 전체적인 톤앤매너를 통일합니다.

### [Node 8] Wait for Webhook: 생성 완료 웹훅 대기 (비동기 이벤트 리스너)
* 별도의 LLM 프롬프트가 없는 시스템 로직 노드
####목표: 로컬 GPU(Intel Arc)가 이미지 생성을 마칠 때까지 n8n 워크플로우를 '일시 중단(Suspend)' 상태로 전환하여 시스템 자원(CPU/RAM) 소모를 방지합니다. 반복적인 폴링(Polling) 루프를 제거함으로써 부하를 최적화하고, 완료 신호가 도착하는 즉시 지연 없이 다음 단계로 데이터를 전달합니다.   
#### 동작 로직 (Mandatory Logic)
(1) 웹훅 기반 비동기 대기 (Webhook-based Wait):n8n의 'Wait' 노드를 'On Webhook Call' 모드로 설정합니다.   
[핵심 설정]: 
- 반드시 'Resume Key' 옵션을 활성화하여 가변적인 웹훅 호출에 대비합니다.   
- Node 7에서 ComfyUI로 작업 요청을 보낸 직후, 시스템은 수신된 웹훅의 JSON 본문 안에 있는 resumeKey 값이 현재 대기 중인 씬의 prompt_id와 일치할 때만 대기를 해제하고 다음 단계로 진행하도록 강제합니다.   

(2) 정밀 세션 복구 및 데이터 매칭 (Resume & Data Matching):
- ComfyUI가 이미지 생성을 완료한 후 웹훅으로 보내온 결과 데이터(prompt_id, file_path 등)를 수신합니다.   
- 수신된 prompt_id를 현재 대기 중인 n8n 실행 세션의 Resume Key와 대조합니다.   
- 이 과정을 통해 수십 개의 씬이 동시에 생성되는 장편 환경에서도 어떤 씬의 이미지가 완성되었는지 100% 정확하게 식별하여 데이터 혼선을 원천 차단합니다.   
- 매칭이 성공하면 대기 상태를 즉시 해제(Resume)하고, 수신된 파일 경로 데이터를 [Node 9] 단계로 안전하게 전달합니다.   

(3) 타임아웃 예외 처리 (Timeout Handling):
- GPU 에러, ComfyUI 중단, 또는 네트워크 문제로 인해 웹훅 신호가 영구히 오지 않을 경우를 대비하여 최대 대기 시간(예: 300초)을 설정합니다.   
- 타임아웃 발생 시 에러 트리거를 작동시켜 해당 챕터의 생성(Node 7)을 최대 3회 자동 재시도(Retry)합니다.

(4) 최종 실패 대응 (Plan B & Monitoring)
- 단계별 대응:
    1) 3회 재시도 실패 시 긴급 알림: 자동 복구가 불가능하다고 판단시, 관리자의 메신저(Telegram)로 "챕터 NN번: 웹훅 수신 실패 (Timeout)" 메시지와 함께 마지막 에러 로그를 즉시 전송합니다.   
    2) 더미 데이터 주입: 에러 로그 전송 후, 실패한 해당 씬만 'N초 블랙 더미 영상' 정보를 주입하여 파이프라인이 나머지 챕터의 렌더링과 최종 병합을 완주할 수 있도록 보장합니다.(씬별 길이에 따라 더미 영상 길이를 설정할 것)

## Step 3: 파일 규격화 및 패키징 (Asset Packaging)
- 생성된 투명 에셋들의 이름을 정리하고 조립에 적합하도록 병합하는 단계입니다.


## [Node 9] Code / Merge: 파일명 규격화 및 씬 단위 병합 (Packaging)
#### 목표: ComfyUI에서 비동기적으로 생성된 다양한 에셋(캐릭터, 소품, 배경, 전경)의 난수 파일명을 규격화하고, 챕터/씬 계층 폴더로 물리적으로 정리한 뒤 최종 에셋 경로 목록을 다음 노드로 전달합니다. WebP lossless 변환을 통해 파일 크기 50% 감소 + 디코딩 시간 10% 절감을 달성합니다.
#### 동작 로직 (JavaScript):
(1) 엄격한 명명 규칙 강제 (Strict Naming Convention):
- ComfyUI가 출력한 난수 형태의 파일명(예: ComfyUI_00123_.png)을 정규화된 이름으로 일괄 변경(Rename)합니다.
- 규격화 규칙 (Node 4의 scene_asset_id를 그대로 파일명에 사용):
  * 배경(asset_type=background, 단일): scene_NN_bg.webp
  * 캐릭터(asset_type=character, 다중 가능): scene_NN_<scene_asset_id>.webp  (예: scene_03_character_01.webp, scene_03_character_02.webp)
  * 소품(asset_type=prop, 다중 가능): scene_NN_<scene_asset_id>.webp  (예: scene_03_prop_01.webp, scene_03_prop_02.webp)
  * 전경(asset_type=foreground, 선택적): scene_NN_foreground.webp

(1-1) WebP lossless 변환 (BN-2 보정):
- ComfyUI 출력 PNG를 sharp 라이브러리 또는 cwebp CLI로 WebP lossless로 변환합니다.
- 알파 채널 무손실 보존, 평균 파일 크기 50% 감소 (1MB → 500KB).
- 디스크 압박 시 운영자가 단계적 lossy 95%로 전환 가능 (CLI 옵션 변경만으로).
- 변환 실패 시 원본 PNG 유지 (안전 폴백).

(2) 물리적 파일 이동 및 폴더 정리 (Physical Organization):
- 모든 에셋을 project/asset/<chapter_id>/<scene_id>/ 계층 폴더로 이동합니다 (장편 영상에서 챕터별 scene_NN 충돌 방지).
- 예: project/asset/chapter_01/scene_03/scene_03_character_01.webp

(3) 에셋 경로 목록 추출 (Asset Path Metadata) — MO-5 보정 (regions 스키마):
- 물리적 정리가 완료된 파일들의 상대 경로 정보를 담은 경량 JSON을 생성합니다.
- 모든 씬은 regions 객체로 자산을 계층화합니다. layout(분할 화면)이 없는 일반 씬은 regions.default 1개로 폴백, layout이 활성화된 씬은 regions.<region_id>로 분리됩니다.
- panel 개념은 폐기되고 layer + split-region 구조로 통합됩니다 (v4.5 §4.5.1 보정).
- 데이터 구조 (정식 스키마):
  JSON {
    "chapter_id": "chapter_01",
    "scenes": {
      "scene_03": {
        "regions": {
          "default": {
            "bg": "project/asset/chapter_01/scene_03/scene_03_bg.webp",
            "characters": [
              {
                "scene_asset_id": "character_01",
                "path": "project/asset/chapter_01/scene_03/scene_03_character_01.webp",
                "position": "left",
                "z_index": 100
              }
            ],
            "props": [
              { "path": "project/asset/chapter_01/scene_03/scene_03_prop_01.webp", "z_index": 50 }
            ],
            "foreground": {
              "path": "project/asset/chapter_01/scene_03/scene_03_foreground.webp",
              "zoom_rate": 1.25
            }
          }
        }
      },
      "scene_07": {
        "regions": {
          "left": { "bg": "...", "characters": [...] },
          "right": { "bg": "...", "characters": [...] }
        }
      }
    }
  }
  * 단일 캐릭터 씬의 경우에도 characters는 1원소 배열로 출력합니다.
  * foreground가 없는 region은 객체 자체를 생략합니다 (null/빈 객체 금지 — Node 10이 'foreground' in region 으로 분기).
  * Node 4 출력의 모든 자산은 region_id 필드를 가져야 합니다 (분할 없는 씬은 자동 "default").
  * 핵심 변경 사항: 이 단계에서는 연출 기획안(Node 3)이나 립싱크 데이터(Node 2)를 병합하지 않고, 오직 이미지 파일의 경로 데이터만 정확히 확정하여 전달합니다.

#### 결과:
- 모든 에셋이 로컬 디스크의 지정된 위치에 정돈됩니다.
- 다음 단계인 Node 9.5(Asset Archiver) → Node 10(Master Assembler)이 '어떤 파일을 가져와야 하는지' 알 수 있는 깨끗한 경로 리스트를 제공합니다.


## [Node 9.5] Asset Archiver: 자가 발전 라이브러리 자동 등재 (구조적 노드) — CL-3 보정
#### 목표: Node 4가 generate_asset:true로 마킹한 신규 창작 에셋을 references_catalog.json의 auto_generated_assets 카테고리에 자동 등재하여, 다음 영상 제작 시 재사용 가능하도록 자가 발전 라이브러리를 구축합니다.
#### 동작 로직 (n8n Code Node - JavaScript):

(1) 대상 필터링
- 입력: Node 9가 정규화한 scene_NN_<scene_asset_id>.webp 경로
- 트리거 조건: Node 4 출력에 generate_asset:true 마킹된 항목만 (caches L1/L2/L3 히트는 자동 제외)
- 비대상은 그대로 통과 (Node 10으로 전달, no-op)

(2) 사본 저장 (Deep Copy)
- 원본 파일은 씬 폴더(project/asset/<chapter_id>/<scene_id>/)에 그대로 유지
- 사본을 assets/static/auto_generated/<auto_yyyymmdd_<hash>>.webp 경로로 저장
- 파일명 hash: SHA1(asset_id + created_at)의 앞 12자

(3) File Lock 보호 (W-7)
- references_catalog.json.lock 파일을 atomic하게 생성/제거 (proper-lockfile 라이브러리 사용)
- read-modify-write 사이클을 단일 트랜잭션으로 처리
- n8n 워크플로우 직렬 mutex로 추가 보호

(4) auto_generated_assets 등재 메타데이터
{
  "asset_id": "auto_<hash>",
  "display_name": "<Node 4 출력의 한국어 이름>",
  "description_search": "<화풍 토큰 제거 핵심 명사구>",
  "description_render": "<화풍 앵커 포함 풀 프롬프트>",
  "tags": ["<영문 태그 배열>"],
  "file_path": "assets/static/auto_generated/auto_<hash>.webp",
  "created_at": "<ISO 타임스탬프>",
  "usage_count": 0,
  "source_video_id": "<현재 video_id>",
  "seed": "<생성 시드>",
  "lora_signature": "<LoRA 이름+가중치 해시>",
  "style_anchor_version": "<글로벌 화풍 앵커 버전>"
}

(5) hnswlib 인덱스 갱신 (BN-5)
- references_catalog.idx 인덱스 파일에 description_search 임베딩을 즉시 addPoint
- 임베딩 모델: 로컬 sentence-transformers/all-MiniLM-L6-v2 (384차원, CPU 100ms/쿼리)
- 인덱스 갱신 실패 시 카탈로그 등재는 유지하되 경고 로그 (다음 영상 시 재인덱스 가능)

(6) 비대화 방지
- usage_count == 0이고 6개월 이상 미사용된 항목은 운영자가 수동 청소 (자동 삭제 금지 — 운영 안전)
- VIVID Step 4 UI의 "이펙트 라이브러리 사용횟수 확인" 버튼이 카탈로그 통계를 시각화 (EF-7)

(7) 오류 방어
- 사본 저장 실패 시: 원본 보존 후 Telegram 경고 (영상 완성에는 영향 없음)
- 카탈로그 갱신 실패 시: 잠금 충돌이면 최대 5회 재시도, 그 외엔 경고 로그 후 통과 (다음 영상 빌드 시 재시도 가능)


## Step 4: 시네마틱 코드 조립 (Cinematic Code Assembly)

### [Node 10] Master Assembler: 데이터 병합 및 HTML 빌더 (The Orchestrator)
#### 목표: Node 3의 연출 기획, Node 9의 에셋 경로, Node 2의 립싱크 데이터, project_config.json의 브랜딩, 그리고(있을 경우) 과제 6 모션 코믹 편집기의 delta JSON을 통합하여 template.html에 주입하고 실행 가능한 chapter_NN.html을 생성합니다. LLM 호출 없이 JavaScript Code Node만으로 작동.

#### 동작 로직 (n8n Code Node - JavaScript):

(1) 입력 데이터 로드 (Input Loading):
- 데이터 A (연출): project/plan/<chapter_id>_plan.json — Node 3 산출, scenes[]에 scene_id, start_time, end_time, character_pose, camera_choreography(x/y/scale/ease), kinetic_typography(text/easing/appear_time/duration), characters[] (다중 캐릭터 메타), vfx_active, ambient_effect, scene_transition, structure_logic 포함.
- 데이터 B (에셋): Node 9 산출 — { chapter_id, scenes: { scene_id: { bg, characters[], props[], foreground? } } }.
- 데이터 C (립싱크): project/lipsync/<chapter_id>_lipsync.json — Node 2 산출, [{ start, end, mouth }] 배열. 챕터 내부 0초 기준.
- 데이터 D (브랜딩): project_config.json — baseline + per_video_overrides[video_id] 조회. 없으면 randomization_rules에 따라 video_id 결정론 시드로 산출 후 per_video_overrides에 영구 기록.
- 데이터 E (편집 delta, 선택): project/edits/<chapter_id>_edits.json — 과제 6 편집기 산출. 존재 시 (3) 단계에서 머지.

(2) 데이터 통합 — 씬 단위 머지 (Per-Scene Merge) — CL-4 보정 (시간 변환 표):

| 필드 | 입력 단위 | Node 10 변환 |
|---|---|---|
| scene.start_time, end_time | 챕터 0초 | 그대로 |
| scene.lipsync[].start, end | 챕터 0초 | 그대로 |
| scene.kinetic_typography.appear_time, duration | 챕터 0초 | 그대로 |
| scene.data_layer.appear_time, duration (v4.5) | 씬 0초 | + scene.start_time |
| scene.layout.trigger_time, duration (v4.5) | 씬 0초 | + scene.start_time |
| scene.manga_effects[].start_time, duration (v4.5) | 씬 0초 | + scene.start_time |

- 머지 규칙:
  * scene_id, start_time, end_time, structure_logic, scene_context: plan에서 그대로 복사
  * camera_choreography, kinetic_typography, vfx_active, ambient_effect, scene_transition: plan에서 그대로 복사
  * assets.regions: Node 9 산출에서 복사 (regions.default 또는 regions.<region_id> 구조)
  * regions[*].characters: Node 9의 characters 배열 + plan의 characters[].position/z_index를 scene_asset_id 키로 매칭하여 머지 (Node 9가 이미 머지해 보내는 경우 그대로 통과)
  * lipsync: Node 2의 통짜 챕터 배열 중 cue.start ∈ [scene.start_time, scene.end_time)인 항목만 필터링하여 scene.lipsync로 부여 (시간값 그대로)
  * v4.5 시간 필드(data_layer/layout/manga_effects): 위 표대로 scene.start_time을 더해 챕터 좌표로 변환
- emotion_timeline 필드는 BN-1 결정에 따라 폐기 (v4.5에서 도입했으나 ComfyUI 호출 부하 가중 우려로 제거).

(3) 편집 delta 머지 (Edit Delta Merge — 과제 6 산출물):
- project/edits/<chapter_id>_edits.json 파일이 존재하면 로드하여 씬 단위로 deep-merge.
- 충돌 시 delta가 plan/asset 값을 덮어쓴다 (편집기에서 사용자가 한 결정이 LLM 기획보다 우선).
- delta가 없거나 파일이 없으면 본 단계는 no-op.

(4) 브랜딩 결정론 산출 (Deterministic Branding) — EF-6 보정:
- per_video_overrides[video_id]가 이미 있으면 읽기만 수행, 쓰기 스킵 (동일 영상 챕터 N개에 대해 단 1회만 디스크 갱신).
- 없으면 video_id 문자열을 cyrb53 해싱 → mulberry32 PRNG로 randomization_rules의 모든 키(watermark_x/y/opacity, accent_hue/sat, vignette_alpha) 산출 → clamp/wrap/decimals 적용 → per_video_overrides[video_id]에 기록 후 디스크 저장 (1회).
- 산출된 객체를 DATA.branding으로 그대로 주입.
- 디스크 I/O 충돌 방지: 영상 단위 1회 갱신 정책 + File Lock(W-7) 보호.

(5) 최종 DATA 구조화 (Final Schema):
- template.html이 소비하는 정확한 형태:
  JSON {
    "meta": {
      "video_id": "<string>",
      "chapter_id": "<chapter_NN>",
      "fps": 30,
      "duration": <챕터 총 초 — 마지막 scene.end_time>,
      "render_mode_default": false
    },
    "branding": {
      "watermark_x": <px>, "watermark_y": <px>, "watermark_opacity": <float>,
      "vignette_alpha": <float>, "accent_hue": <int>, "accent_sat": <int>
    },
    "scenes": [
      {
        "scene_id": "scene_01",
        "start_time": 0.0, "end_time": 12.0,
        "assets": { "bg": "...", "characters": [...], "props": [...], "foreground": {...}? },
        "camera_choreography": { "x": 0, "y": 0, "scale": 1.0, "ease": "power2.inOut" },
        "kinetic_typography": { "text": "...", "easing": "bounce", "appear_time": 4.5, "duration": 6.5 },
        "lipsync": [ { "start": 0.5, "end": 1.2, "mouth": "B" }, ... ],
        "vfx_active": false,
        "ambient_effect": { "type": "none" } | { "type": "rain", "intensity": "medium", "wind_angle": 30 },
        "scene_transition": "cut" | "fade_black" | "glitch" | "zoom_blur" | "slide_left"
      }, ...
    ]
  }
- 모든 시간값은 챕터 내부 0초 기준 (§Node 1).
- scenes 배열은 start_time 오름차순으로 정렬.

(6) 템플릿 로드 및 주입 (Template Injection):
- shared_assets/template.html 파일을 UTF-8로 읽어옵니다.
- 정확히 한 번 등장하는 플레이스홀더 토큰 `{{INJECTED_JSON}}` (또는 prettier로 인해 `{{ INJECTED_JSON }}`로 띄어쓰기된 변형 모두)을 JSON.stringify(DATA)로 치환합니다.
- 토큰이 0회 또는 2회 이상 등장하면 즉시 에러를 던지고 Telegram 알림을 보냅니다 (template.html 무결성 보호).

(7) 물리적 저장 (Physical File Save):
- 출력 경로: project/compositions/<chapter_id>.html (예: project/compositions/chapter_01.html).
- 동일 경로 파일이 존재하면 덮어쓰기 (Node 11이 항상 최신본을 렌더하도록).

(7-1) lazy 이미지 로드 정책 (EF-5 보정):
- DATA.scenes[*].regions[*]의 모든 이미지에 loading_strategy: "lazy" 메타 마킹.
- template.html buildScenes()가 활성 씬 + 다음 1씬만 src 주입, 나머지는 빈 src로 DOM 생성.
- 씬 스위처 발동 시 다음 다음 씬 이미지 미리 로드.
- 챕터당 메모리 사용량 5분의 1 수준으로 감소 (160MB → 30MB 수준).

(8) 오류 방어 (Error Handling):
- 입력 파일 5종 중 plan/asset/lipsync는 필수, branding/edits는 선택.
- 필수 파일 누락 또는 JSON 파싱 실패 시 Telegram 알림 후 일시정지.
- DATA.scenes가 비어 있거나 scene.regions.default.bg가 없는 씬이 하나라도 있으면 경고 로그 + 더미 검은 배경(#000) 자동 채움 (파이프라인 완주 보장).

(9) n8n Code Node 환경 요구사항:
- 외부 npm 모듈 불필요 (fs, path, crypto 등 Node.js 빌트인만 사용).
- 코드 본체는 별도 파일 n8n_workflow/nodes/node10_master_assembler.js로 관리하며, n8n Code Node에는 본 파일 내용을 그대로 붙여넣습니다.

## Step 5: 최종 렌더링 및 장편 병합 (Final Export & Merge)

### [Node 11] Cinematic Renderer: 시네마틱 렌더링 (The High-End Renderer)
#### 목표: 저장된 각 챕터별 HTML 파일을 Hyperframes CLI를 이용해 개별 MP4 영상으로 변환합니다.  

#### 동작 로직 (Operational Logic):

(1) HyperFrames 호출:
- n8n의 Execute Command 노드가 Node 10에서 생성된 HTML 파일 경로를 참조하여 렌더링 명령어를 실행합니다.  
- 명령어 예시: hyperframes render ./compositions/chapter_01.html --output ./render/chapter_01.mp4   

(2) Stateless 렌더링 방식 강제 (EF-3 — 현재 정책 유지):
- HyperFrames CLI 호출 시 이전 챕터의 캐시나 메모리 점유가 남지 않도록 매 챕터 렌더링이 끝날 때마다 Chromium(또는 Puppeteer) 인스턴스를 완전히 종료(kill 프로세스)하고, 챕터별로 새 인스턴스를 띄우는 방식을 강제하여 메모리 누수를 방어합니다.
- 이 정책으로 챕터당 5~10초의 재시작 손실이 발생하지만, 본 렌더 3.5~6시간 대비 0.3~0.5%로 무의미 → 안정성 우선 채택.
- boil 필터 (10fps SVG 필터 swap)는 본 렌더에서 비활성화하여 프레임당 처리 시간 약 30% 절감 (BN-2 보정).

(3) 챕터 단위 직렬 + 이종 작업 파이프라이닝 (Sequential + Asynchronous Pipelining):
- VRAM 8.9GB 제약(§1.2)에 따라 챕터별 동시 렌더링은 금지합니다. 챕터 단위 HyperFrames 호출은 반드시 순차 실행합니다.
- 단, GPU 자원이 한가하지 않도록 N번 챕터를 HyperFrames(CPU/Chromium)로 렌더링하는 동안 N+1번 챕터의 Node 7(ComfyUI/GPU) 에셋 생성을 동시에 진행시키는 이종 작업 교차 진행 구조를 채택합니다.
- 이를 위해 n8n 워크플로우는 챕터 인덱스 기반으로 Node 7(다음 챕터)과 Node 11(현재 챕터)을 비동기적으로 디스패치하되, 각자의 큐는 단일 직렬을 유지합니다.

(4) HyperFrames 렌더 모드 진입 시 Seek 강제 (Render-mode Flag):
- HyperFrames CLI는 환경 플래그(예: ?render=1 또는 window.VIVID_RENDER_MODE=true)를 통해 template.html을 호출하여, 자동 requestAnimationFrame 루프를 비활성화하고 외부에서 window.VIVID_SEEK(t)로만 타임라인을 구동하도록 강제합니다.
- 이는 rAF 자동 진행과 외부 seek가 동시에 작동하여 프레임 시간이 어긋나는 현상을 원천 차단하기 위함입니다.

(5) 렌더링 실패 시 최대 2회 재시도:
- 챕터 렌더링 최종 실패 시 해당 챕터만 건너뛰고 관리자에게 에러 로그 전송(Telegram).

(6) Stop & Resume 메커니즘 (장편 본 렌더 안전성):
- 본 렌더 3.5~6시간 도중 임의 챕터 실패 또는 운영자 중단 시, 이미 완성된 챕터는 재렌더링하지 않습니다.
- 진입 검사 (HyperFrames 호출 직전):
  * 검사 1: `project/render/<chapter_id>.mp4` 파일이 존재하고 크기 > 0인가?
  * 검사 2: `project/compositions/<chapter_id>.html`의 SHA256 해시와 `project/render/<chapter_id>.mp4.meta` 파일에 기록된 입력 해시가 동일한가?
  * 검사 3: `project/plan/<chapter_id>_plan.json` + `project/asset/<chapter_id>/`의 mtime이 mp4 파일 mtime보다 이르거나 같은가?
- 세 검사 모두 PASS면 Node 11을 스킵하고 기존 mp4 경로를 Node 12로 그대로 전달.
- 어느 하나라도 FAIL이면 정상 렌더 수행, 완료 후 `<chapter_id>.mp4.meta`에 입력 해시 기록.
- meta 파일 스키마: `{ "html_sha256": "<hex>", "rendered_at": "<ISO 타임스탬프>", "hyperframes_version": "<버전>" }`
- 운영자 강제 재렌더 시 `<chapter_id>.mp4` 또는 `.meta` 파일을 수동 삭제하면 다음 실행에서 재렌더.
- 본 메커니즘은 Node 7 캐시(L3 SHA1) 및 Node 10 chapter_NN.html 캐시와 직교하며, 가장 비싼 단계인 본 렌더만 보호합니다.



### [Node 12] Final Merge & Cleanup: 최종 병합 및 마무리
#### 목표: 조각난 MP4 파일들을 FFmpeg로 결합하여 최종 영상을 완성하고, 임시 파일을 정리하여 파이프라인을 종료합니다. 
#### 동작 로직 (Operational Logic):
(1) FFmpeg 최종 병합: 모든 챕터의 MP4 파일 생성이 완료되면 FFmpeg를 호출하여 무손실(Concat) 방식으로 영상을 이어 붙입니다.
* FFmpeg Concat 실행 전, `Test-Path` 명령어를 통해 모든 챕터 파일의 물리적 존재 여부를 먼저 검사합니다.
* **동적 결합 및 순서 통제**:FFmpeg 병합 목록을 Node 1에서 생성된 챕터 배열 순서 그대로 생성하여 결합합니다.  
* 결합 순서: 인트로 ➡️ 범퍼 비디오(동적 위치) ➡️ 본문 ➡️ 아웃트로.  

(2) 인코딩 지문 분산 (Fingerprint Randomization) — EF-4 보정:
- 자동화 파이프라인의 기계적 일관성을 수학적으로 파괴하기 위해 FFmpeg 호출 시 다음 파라미터 조합 사용 (양산 검열 회피 유지):
  * CRF: 영상마다 19~21 사이 무작위 (절대 화질 방어)
  * maxrate: 14M, bufsize: 28M (CRF 모드 상한 제어)
  * GOP size(-g): 챕터마다 다르게 부여 (90~150 사이 무작위)
- CRF + maxrate 조합으로 비트레이트 무작위와 화질 보장 동시 달성.
- 챕터마다 다른 GOP + 영상별 CRF 변동만으로도 SSIM 기반 양산형 판정 회피에 충분.
- Intel Quick Sync(h264_qsv) 하드웨어 가속 사용 — 인코딩 시간 50% 절감 (BN-2 보정).
  * 명령어 예시: ffmpeg -i input.mp4 -c:v h264_qsv -global_quality 20 -maxrate 14M -bufsize 28M -g 120 output.mp4

(3) 자동화된 쓰레기 파일 정리 (Garbage Collection):
- 렌더링 성공 종료 후 임시 이미지 파츠 및 병합 전의 MP4 조각들을 자동으로 삭제하여 디스크 용량을 확보합니다.

(4) 해상도 및 프레임 규격 통제
- 1920x1080 해상도, 30fps(또는 60fps), H.264 코덱 규격을 엄격히 준수합니다.

(5) FFmpeg 병합 실패 시 로직 : 
- FFmpeg 병합 실패 시 concat 리스트와 에러 로그를 관리자에게 전송하고 일시 정지.


## Step 6: Vrew 프로젝트 패키징 (Vrew Project Packaging)

### [Node 13] Vrew Project Builder: 원본 .vrew에 비디오 트랙 주입 (구조적 노드)
#### 목표: Vrew에서 TTS/자막 편집이 완료된 원본 .vrew 프로젝트 파일을 열어, 파이프라인이 렌더링한 챕터별 MP4 영상을 비디오 트랙으로 주입한 뒤 다시 .vrew로 패키징합니다. 자막, TTS 오디오, 단어별 타이밍 등 Vrew가 이미 완성한 데이터는 일절 수정하지 않습니다.

#### 정식 레퍼런스 구현 (Source of Truth)
- 동일 동작이 `utils/backend_ext.py > assemble_vrew_hf()`에 Python으로 이미 구현·검증되어 있습니다.
- 본 명세는 그 구현을 정식 레퍼런스로 삼으며, n8n Code Node(JavaScript)는 이 함수를 1:1로 포팅합니다.
- 실제 .vrew의 project.json 스키마는 `vrew_check/project.json`에서 직접 확인 가능합니다.

#### 핵심 원칙: 원본 보존 + 비디오만 주입
- 원본 .vrew의 project.json 내 transcript(자막/단어 타이밍), TTS 트랙, 기존 에셋 매핑은 그대로 유지합니다.
- 오직 렌더링된 챕터별 MP4 비디오 트랙만 추가합니다.
- 이 방식을 통해 Vrew의 정밀한 단어별 타임코드와 TTS 세그먼트를 100% 활용하면서, 자체 제작한 모션 코믹 영상을 Vrew 편집 환경에 바로 올릴 수 있습니다.

#### 동작 로직 (n8n Code Node - JavaScript):

(1) 원본 .vrew 파일 언팩 (Unzip) — RAM 폭발 방어 정책
- Node 1에서 보존된 원본 .vrew 파일 경로를 참조하여 **디스크 임시 추출 + 재패키징** 방식으로 처리합니다.
- 30분 영상 = 챕터별 MP4 합산 1~2GB. adm-zip 등 인메모리 ZIP 라이브러리 사용 시 n8n Code Node RAM 폭발 위험 (특히 Docker/n8n cloud 환경 OOMKilled).
- 작동 절차:
  * (a) `os.tmpdir()/vrew_<run_id>/` 임시 디렉토리 생성
  * (b) 원본 .vrew를 임시 디렉토리에 전체 추출 (스트림 기반 unzip — adm-zip의 extractAllToAsync도 디스크 직쓰기로 동작)
  * (c) project.json만 메모리에 로드 (수 MB 수준), 수정 후 디스크 덮어쓰기
  * (d) 챕터별 MP4를 임시 디렉토리의 `media/` 폴더로 복사
  * (e) 디스크의 임시 디렉토리를 다시 ZIP으로 재패키징 (스트림 기반 zip)
  * (f) 결과물을 `최종_hf_vN.vrew`로 이동 후 임시 디렉토리 삭제
- RAM 사용량은 ZIP 크기와 무관하게 수십 MB 수준으로 일정. 임시 디스크 사용량 ~2GB는 SSD 환경에서 무시 가능.
- project.json과 기존 media/ 항목은 (b)~(c) 단계에서 디스크 상에 그대로 보존됩니다.

(1-1) 기존 files[] 절대 경로 정규화 (Path Normalization)
- project.json의 files[] 항목 중 filePath / localPath / sourcePath / path 필드에 절대 경로(C:\..., /home/..., 역슬래시 포함 경로)가 있으면 basename(파일명)만 남기도록 변환합니다.
- 다른 PC에서 .vrew를 열 때 절대 경로 깨짐을 사전 차단합니다. (assemble_vrew_hf의 _normalize_file_paths 동작과 동일.)

(2) project.json files[] 배열에 MP4 등록 (Media Registration)
- 챕터별 렌더링된 MP4 각각에 UUID 기반 mediaId를 생성하고, 다음 정확한 스키마로 등록합니다:
  * version: 1
  * mediaId: UUID
  * sourceOrigin: "USER"
  * fileSize: mp4 바이트 크기 (fs.statSync().size)
  * name: `${mediaId}.mp4` (반드시 mediaId 기반 — 원본 파일명 사용 금지)
  * type: "AVMedia"
  * videoAudioMetaInfo: { duration: <ffprobe로 추출한 초>, videoInfo: { codec: "h264", frameRate: 30 } }
    - 주의: videoInfo에 size 필드는 넣지 않습니다. 실제 Vrew는 codec / frameRate만 요구합니다.
  * sourceFileType: "VIDEO_ONLY" (HF 렌더 mp4 = 비디오 단독, 오디오 트랙 없음)
  * fileLocation: "IN_MEMORY"

(3) props.tracks{}에 비디오 트랙 추가 (Video Track Injection)
- 각 챕터 MP4에 대해 10자 영숫자 랜덤 trackId를 생성하고 props.tracks[trackId]에 다음 객체를 등록합니다:
  * trackId, mediaId
  * xPos: 0.0, yPos: 0.0, width: 1.0, height: 1.0 (전체화면 정규화 좌표)
  * rotation: 0
  * zIndex: 10 (HF 슬라이드는 메인 풀스크린 레이어로 배치 — 명세 V3까지의 "낮은 zIndex" 표현은 잘못된 추측이었으며, 실제 backend_ext.py는 10을 사용)
  * type: "video"
  * sourceIn: 0
  * sourceOut: round(duration, 3)
  * hasAlphaChannel: false (불투명 풀스크린)
  * isTrimmable: true
  * editInfo: {}
  * fillType: "cut"
- 별도의 type: "videoAudio" 트랙은 생성하지 않습니다 (HF mp4는 무음이며, 기존 TTS 트랙이 음원을 담당).

(4) transcript.clips에 비디오 에셋 연결 (Asset Binding) — CL-5 보정:
- 클립 타이밍 계산: project.transcript.clips 각각에 대해 words[].duration을 누적해 [start, end) 초를 산출합니다 (assemble_vrew_hf의 _compute_clip_timings 동일 로직).
- 챕터별 mp4의 시작 시간으로 Node 1의 chapter_meta[].chapter_global_start를 우선 사용 (워크플로우 전역에서 보존). mp4 duration 누적은 fallback일 뿐.
  * 이유: -c copy 분할 시 keyframe 경계 보정으로 챕터 mp4 누적 길이가 원본 글로벌 시간과 ±수십 ms 어긋날 수 있음. 글로벌 시작 시간을 직접 사용하여 clip 매칭 정밀도 보장.
- 그 시간(start_sec)이 [clip.start, clip.end) 범위에 들어가는 첫 클립을 찾아 해당 clip.assetIds 배열에 신규 asset_id(UUID)를 push합니다.
- 매칭되는 클립이 없으면 마지막 클립에 매핑합니다 (fallback).
- props.assets[asset_id] 등록: { trackIds: [trackId], role: "sub" }
  - role:"sub"는 기존 TTS(role:"main")와 공존하기 위한 필수 값입니다.

(5) media/ 폴더에 MP4 삽입 (Physical File Copy)
- 챕터별 MP4를 ZIP 내부 `media/${mediaId}.mp4` 경로로 기록합니다.
- 파일명은 반드시 mediaId 기반 — 원본 chapter_01.mp4 같은 이름을 그대로 쓰면 Vrew가 매핑을 못 찾습니다.

(6) 재패키징 (Re-zip & Versioned Output) — 디스크 기반
- 출력 경로 자동 버저닝: asset_dir 안에 `최종_hf_v0.vrew`, 존재하면 `최종_hf_v1.vrew` … 식으로 자동 증분 (assemble_vrew_hf와 동일 규칙).
- ZIP 재조립 절차 (디스크 기반, RAM 폭발 방어):
  * 임시 디렉토리(1단계 (b))에 이미 모든 원본 항목과 신규 mp4가 디스크 상에 정렬되어 있음
  * project.json은 (1)-(c) 단계에서 이미 디스크 덮어쓰기 완료 (`JSON.stringify(project)` separators 없음, ensure_ascii=false 동등)
  * 신규 mp4는 (1)-(d) 단계에서 이미 임시 `media/${mediaId}.mp4`로 복사 완료
  * 임시 디렉토리 전체를 스트림 기반 zip으로 재패키징하여 `최종_hf_vN.vrew` 생성
  * 재패키징 완료 후 임시 디렉토리 삭제 (디스크 회수)
- 확장자는 .vrew 그대로.

(7) 오류 방어 (Error Handling)
- 원본 .vrew 언팩 실패 또는 project.json 파싱 실패 시 관리자에게 Telegram 알림 후 일시정지합니다.
- 이 경우에도 MP4 최종 영상은 Node 12에서 이미 완성된 상태이므로 영상 자체는 보존됩니다.
- ffprobe 호출 실패 시 해당 mp4의 duration을 0으로 두지 않고, Node 1에서 산출된 챕터별 글로벌 길이를 fallback 값으로 사용합니다.

(8) n8n Code Node 환경 요구사항
- 외부 npm 모듈 허용: 환경 변수 `NODE_FUNCTION_ALLOW_EXTERNAL=adm-zip` 설정 필수 (extractAllToAsync로 디스크 직쓰기, 스트림 unzip만 사용 — 인메모리 readZip 금지).
- 시스템 PATH에 ffprobe(FFmpeg 패키지에 포함) 가용 필수.
- OS 임시 디렉토리(`os.tmpdir()`) 쓰기 권한 필수 — 30분 영상 처리 시 ~2GB 임시 공간 소요.
- 코드 본체는 별도 파일 `n8n_workflow/nodes/node13_vrew_builder.js`로 관리하며, n8n Code Node에는 이 파일 내용을 그대로 붙여넣습니다.

(9) 진입 조건 강제 — 1회 호출 보장 (EF-8 보정):
- Node 13은 반드시 모든 챕터 mp4 산출이 완료된 후 1회만 호출되어야 합니다.
- n8n 워크플로우에서 Node 12와 Node 13 사이에 Aggregate(또는 Merge) 노드를 명시적으로 배치하여, 모든 챕터 아이템이 합쳐진 단일 입력으로 Node 13에 전달.
- 챕터마다 호출 시 .vrew 풀 재패키징(ZIP 압축) I/O 폭발이 발생하므로 단일 호출 정책 절대 준수.

#### 장점:
- Vrew TTS 엔진이 생성한 정밀한 단어별 타임코드를 그대로 활용합니다 (직접 변환 불필요).

#2. 모션 코믹 시각 연출 지침 (v4.0)
##2.1 복합 애니메이션 연출 (2.5D Parallax + Illusion Motion)화면의 깊이감을 조성하고, 관절 분할 없이도 캐릭터의 폭발적인 생동감을 구현합니다.
- Z-Depth 속도 차등: 카메라 이동 시 레이어별 속도(Scale/Position)에 차이를 두어 3D 공간을 시뮬레이션합니다. 배경은 scale 1.05로 천천히, 전경의 통짜 캐릭터와 소품은 scale 1.15로 빠르게 줌인하여 공간감을 극대화합니다.
- 착시형 모션 연출 (Illusion Motion): 물리적인 관절 분할 없이 이미지를 통째로 제어하여 동감을 만듭니다.
- 워킹 일루전 (Walking Illusion): 캐릭터 이동 시 X축 전진과 동시에 Y축으로 짧고 빠른 바운스(yoyo)를 주어 실제로 걷는 듯한 착시를 부여합니다.
- 임팩트 흔들림 (Impact Shake): 강조 포인트에서 캐릭터 전체를 미세하게 진동시켜 타격감을 살립니다.
- 즉각적 포즈/표정 스위칭 (Instant Swapping): 대본의 감정 변화 시 부드러운 전환을 배제하고, 0.1초 이내에 다른 포즈/표정의 통짜 일러스트로 교체하여 애니메이션 특유의 리듬감을 확보합니다.

##2.2 오디오 기반 정밀 립싱크 (Audio-Driven Lip Sync)
성우(.mp3)의 음성 파형에 완벽하게 동기화된 하관 움직임을 구현합니다.
- 스케일 바운스 립싱크 (Scale Bounce Lip-Sync): 발음 구간(A~F)에 맞춰 캐릭터 레이어의 Scale-Y를 1.02배 미세하게 늘리거나 Y축 위치를 조절합니다. 이는 통짜 이미지에서도 턱관절이 열리며 말하는 듯한 역동성을 주는 핵심 착시 기법입니다.
- 파형 기반 레이어 토글: Rhubarb 데이터를 바탕으로 입이 벌어지는 구간에서만 '입 벌림' 오버레이 레이어를 0.15초 간격으로 교차(Toggle)시킵니다.
- 침묵 구간 제어 (Silence Pause): 'X(침묵)' 구간에서는 즉시 모든 바운스와 토글을 멈추고 입을 다문 상태로 대기시켜 어색함을 차단합니다.

##2.3 다이나믹 카메라 워킹 (Dynamic Camera Work)
통짜 일러스트의 단조로움을 극복하기 위해 화면 전체(.scene)를 역동적으로 핸들링합니다.
- 임팩트 줌 (Impact Zoom): 위기 상황이나 핵심 정보 등장 시, 0.3초 이내에 캐릭터의 얼굴이나 팝업 텍스트로 카메라를 강하게 줌인(scale 1.2~1.5)하여 시선을 고정합니다.
- 팔로우 팬 (Follow Pan): 캐릭터의 시선이나 소품의 위치에 따라 카메라 시점을 부드럽게 이동시켜 정보의 흐름을 유도합니다.
- 핸드헬드 셰이크 (Hand-held Shake): 충격적인 대목에서 불규칙한 진동을 주어 현장감과 긴장감을 극대화합니다.

##2.4 시인성 극대화 키네틱 타이포그래피 (Targeted Typography)
5070 시청자층의 시각적 피로도를 낮추고 메시지 전달력을 높입니다.
- 절제된 팝업 (Minimal Pop-up): 대본 전체가 아닌, 핵심 구절만 10자 내외로 화면 여백에 노출합니다.
- 5070 전용 규격: 80px 이상의 초거대 굵은 'Pretendard (Black/900)' 폰트를 사용하여 모바일에서도 가독성을 보장합니다.
- 퍼지는 그림자 (Text-Shadow): 복잡한 누아르 배경에서도 글자가 묻히지 않도록 짙고 넓은 텍스트 그림자(4px 4px 15px)를 강제 적용합니다.
- 맥락 맞춤형 이징 (Easing): 정보의 무게감에 따라 바운스(무거운 정보), 슬라이드(날카로운 지적) 등 GSAP 이징 모션을 차별화합니다.

##2.5 누아르 조명 및 아날로그 질감 (Noir & Texture)
코딩만으로 진중한 경제 전문 채널의 톤앤매너를 완성합니다.
- 세이프 에어리어 블렌딩 (Seamless Bleeding): 하단 자막 영역에 인위적인 검은 띠를 넣지 않고, background: linear-gradient(to top, rgba(0,0,0,0.9), transparent) 등의 CSS 그라데이션을 활용하여 배경 질감이 자막 영역으로 자연스럽게 스며들도록 처리합니다. 이 CSS는 template.html에 하드코딩됩니다
- (보일 이펙트 — BN-2 보정으로 폐기): 본 렌더 프레임당 처리 시간 약 30% 절감을 위해 boil 필터(10fps SVG 필터 swap) 기능 자체를 제거합니다. template.html의 startBoilCycle / applyBoilFilterAtTime / BOIL_FILTERS 모두 폐기.
- 전략적 조명 (Strategic VFX): 상시 조명 대신, 특정 강조 시점에만 비네팅(Vignette)을 강화하거나 경고 맥락에서 붉은색 점멸(Flicker)을 사용하여 시각적 타격감을 줍니다.

##2.6 환경 이펙트 구현 품질 기준 (Ambient Effect Quality Standard)
template.html이 CSS/SVG로 동적 생성하는 환경 효과의 품질 기준입니다. 미리 렌더링된 영상 루프가 아닌, 매번 코드로 생성되므로 씬마다 파티클의 밀도·방향·크기 분포가 달라져 반복감이 없습니다.

- 구현 방식: CSS @keyframes + SVG 필터 기반 동적 생성. template.html의 자바스크립트가 Node 3의 ambient_effect 파라미터(type, intensity, wind_angle)를 읽어 파티클을 런타임 생성합니다.

- 필수 품질 원칙:
  * 개별 랜덤화: 모든 파티클은 크기(scale), 속도(duration), 투명도(opacity), 시작 지연(delay)이 각각 랜덤으로 부여됩니다. 동일한 크기의 점이 같은 속도로 떨어지는 것을 절대 금지합니다.
  * 다층 레이어 깊이감: 파티클을 전경/중경/후경 3개 레이어로 분리합니다. 전경 파티클은 크고 빠르고 흔리게(blur), 후경은 작고 느리고 선명하게 처리하여 2.5D 공간감을 강화합니다.
  * 바람 방향 반영: Node 3의 wind_angle 값에 따라 파티클의 이동 방향을 대각선으로 설정합니다. 비가 수직으로만 떨어지는 것은 부자연스럽습니다.
  * 강도별 밀도 제어: intensity 값에 따라 파티클 수를 light(15~25개), medium(30~50개), heavy(60~100개)로 자동 조절합니다.
  * 모션 블러: 빠른 파티클(비, 눈)에는 CSS filter: blur(1~2px)를 적용하여 속도감을 표현합니다.

- 효과별 핵심 스타일:
  * rain: 길쭉한 선형 파티클 + 대각선 났하 + 바닥 튀김(splash) SVG 애니메이션
  * dust: 불규칙한 크기의 원형 파티클 + 느린 부유 + 미세한 회전
  * light_rays: 상단 코너에서 내려오는 선형 그라디언트 + opacity 맥동(pulse) + 미세 각도 변화
  * smoke: 큰 블로브형 SVG + 가우시안 블러 + 느린 상승 + 투명도 점진적 감소
  * snow: 원형 파티클 + 좌우 흔들림(sinusoidal sway) + 느린 났하

##2.7 프로그레시브 브랜딩 시스템 (Progressive Branding)
채널의 전체적인 톤앤매너는 일관되게 유지하되, 영상마다 시각적 구성을 미세하게 변동시켜 레이아웃 해싱(SSIM) 기반 양산형 판정을 우회합니다. 변동폭은 시청자가 인지하지 못할 수준으로 제한합니다.
- 설정 파일: project_config.json에 영상별 브랜딩 파라미터를 정의하며, template.html이 이 값을 참조합니다.
- 워터마크 위치 미세 변동: 채널 로고/워터마크의 position을 영상마다 ±15px 범위 내에서 변동합니다. (예: 기본 right:30px, bottom:30px → 영상별 right:18~42px, bottom:22~38px)
- 워터마크 투명도 변동: opacity 값을 0.25~0.40 범위 내에서 영상마다 다르게 설정합니다. 
- 색상 팔레트 미세 변동: 채널의 주요 강조색(accent color)의 HSL 값에서 Hue를 ±5도, Saturation을 ±5% 범위 내에서 영상마다 변동합니다. (예: 기본 hsl(220, 80%, 55%) → 영상별 hsl(215~225, 75~85%, 55%))
- 비네팅 강도 변동: 비네팅 그라데이션의 rgba alpha값을 영상마다 0.7~0.95 범위 내에서 변동합니다.
- 변동 원칙: 위 파라미터들의 영상별 구체적 값은 파이프라인이 지정 범위 내에서 자동 랜덤 생성하여 project_config.json에 기록합니다. 모든 변동은 시청자가 "같은 채널의 영상"으로 인지하는 범위 내로 제한합니다.
- 기준값 갱신 (수동 운영): 위 범위의 기준 중심값(예: Hue 220°, right:30px 등)은 운영자가 약 6개월 주기로 직접 project_config.json의 baseline 섹션을 수정하여 점진적으로 갱신합니다. 이는 파이프라인 자동화 범위 밖의 운영 지침입니다.

# ══════════════════════════════════════════════════════════════════
# ※ 본 섹션의 모든 설계 사항은 #1(파이프라인 명세)/#2(시각 연출 지침)에 이미 인라인 반영 완료.
#   본 섹션은 설계 근거 아카이브로만 참조할 것.


##4.1 핵심 설계 원칙
- 하이브리드 렌더링: 생성형 AI(FLUX) 창의성 + HTML/GSAP 데이터 시각화 + 정적 에셋 조립을 단일 파이프라인 안에서 역할 분담.
- 자가 발전 에셋: 영상 제작이 누적될수록 카탈로그 자동 확장 (수동 개입 0).
- AI 창의성 보존: 사전 정의 라이브러리(포즈/정적/이펙트)는 강제가 아닌 선택지. LLM이 매 씬 직접 판단.
- 연출 감독 권한 위임: "언제 AI 쓰고 언제 시스템 통제력을 쓸지"는 Node 3·4가 결정. 본 명세는 결정 도구만 제공.
- 편집 친화 객체 분리: 모든 시각 객체를 처음부터 독립 레이어 + data-edit-id로 분리 (과제 6 미리보기 편집기와 합치).
- 시간 결정론: 모든 라이브러리 애니메이션 자체 타이머 OFF + GSAP 외부 제어 (HyperFrames VIVID_SEEK 결정론과 100% 동기화).

##4.2 하이브리드 포즈 제어 시스템 (Selective ControlNet)
FLUX의 창의 구도를 기본 모드로 두고, 확정적 액션이 필요한 핵심 컷에서만 ControlNet 뼈대 강제 → IP-Adapter '증명사진 현상' 방어.

### 4.2.1 동작 모드 (Node 4 결정)
- Auto (`"pose":"auto"` 또는 생략): IP-Adapter 0.65 / FaceID 0.85, ControlNet 미적용 → FLUX 창의 구도
- Controlled (`"pose":"<pose_id>"`): IP-Adapter 0.30~0.40 / FaceID 0.85 / ControlNet OpenPose 활성

### 4.2.2 정보성 채널 권장 라이브러리 15종 (E-2)
앵커 데스크 정적 8종 (category:"static", 사용 빈도 70%):
- pose_anchor_neutral (양손 책상 위, 정면)
- pose_anchor_explaining_open (양손 벌려 설명)
- pose_anchor_explaining_chop (한 손 수직 가르기)
- pose_anchor_finger_count (검지/중지 카운트)
- pose_anchor_thoughtful (한 손 턱 받침)
- pose_anchor_typing (노트북/태블릿 보며 타이핑)
- pose_anchor_glasses_adjust (안경 고쳐 쓰기)
- pose_anchor_listening (기울인 자세, 청취)

강조 액션 7종 (category:"action", 사용 빈도 20%):
- pose_pointing_data (옆/아래 가리킴)
- pose_pointing_audience (정면/시청자 가리킴)
- pose_emphasis_fist (주먹으로 책상 두드림)
- pose_doc_present (양손으로 서류 제시)
- pose_concerned_lean (책상에 팔꿈치 짚고 기울임)
- pose_arms_crossed_authority (팔짱)
- pose_facepalm_disappointed (한 손 이마/얼굴 짚기)

### 4.2.3 character variant 매칭 (W-2)
- pose_library.json[pose_id].applicable_character_angle 참조하여 가용 variant 중 첫 매칭 선택

### 4.2.4 Node 7 ComfyUI 분기

### 4.2.5 자가 발전: 신규 포즈 누적

##4.3 자가 발전형 에셋 라이브러리 (Auto-Archiving)

### 4.3.1 references_catalog.json 카테고리 4종
- characters: 메인 캐릭터 (FaceID 강제, 다각도 매핑)
- props: 자주 등장하는 소품 레퍼런스 (img2img, denoise 0.5)
- static_assets: 운영자 수동 등재 범용 밈/아이콘 (ID 매칭 전용)
- auto_generated_assets: 자동 등재 신규 소품 (임베딩 검색 대상)

공통 필드: asset_id / display_name / file_path / created_at / usage_count / tags[] / description_search / description_render / style_anchor_version / lora_signature
재생성용 메타데이터: seed (PNG 재사용 시 미사용)

### 4.3.2 글로벌 화풍 앵커 (W-3)
- references_catalog.json 상단에 global_style_anchor 글로벌 변수 신설
- 예: "informative webtoon style, noir economic illustration, bold clean vector lines"
- Node 4의 description_render는 자동으로 글로벌 앵커를 suffix로 주입 (코드 레벨 강제)
- 운영자 6개월 주기 갱신 → style_anchor_version bump → 미스매치 항목은 우선순위 강등(자동 제외 X)

### 4.3.3 Node 4 카테고리 검색 5계층 우선순위 (W-1)
1. characters (match_score ≥ 0.7, FaceID 강제) → ComfyUI 1회 (text2img + FaceID)
2. static_assets (정확 ID 매칭, 임베딩 X) → ComfyUI 0회 (즉시 사용)
3. auto_generated_assets (코사인 ≥ 0.85) → ComfyUI 0회 (PNG 재사용)
4. props (match_score ≥ 0.7) → ComfyUI 1회 (img2img, denoise 0.5)
5. generate_asset:true → ComfyUI 1회 (신규 창작, Node 8.5에서 자동 등재)

### 4.3.4 3계층 캐시 정책 (C-2, EF-1 보정)
- L1 reuse_asset_id 명시 (Node 4 단계): 카탈로그 직접 지정 → ComfyUI 완전 스킵
- L2 임베딩 검색 (Node 4 단계, L1 미적용 시): description_search 코사인 ≥ 0.85 → reuse_asset_id로 합류
- L3 SHA1 캐시 (Node 7 단계, L1·L2 모두 미적용 시): asset_type별 분리 키 적용
  * 캐릭터/소품(asset_type:'character'|'prop'): SHA1(ref_image_id + "|" + prompt + "|" + lora_signature) — seed 제외 (영상 1편 내 동일 시드 정책으로 자연 일관)
  * 배경/전경(asset_type:'background'|'foreground'): SHA1(ref_image_id + "|" + seed + "|" + prompt + "|" + lora_signature) — 씬마다 다른 시드 (화풍 일관성 우선)
  * 본 정책은 §1.3 Node 7 (0) 캐시 키 정책과 1:1 일치

### 4.3.5 [Node 9.5] Asset Archiver — Node 9 직후 (C-1)
- 위치: Node 9 직후로 배치 (난수 파일명 회피, v4.5 초안의 Node 8.5 표기는 폐기되어 9.5로 통일)
- generate_asset:true 마킹 산출물 사본(deep copy)을 assets/static/auto_generated/에 저장 (원본은 씬 폴더 유지)
- File Lock(W-7): references_catalog.json.lock atomic 생성/제거 (proper-lockfile 또는 OS fcntl)
- 카탈로그 갱신 메타데이터 자동 작성

### 4.3.6 임베딩 검색 — 처음부터 hnswlib 도입 (BN-5 보정)
- 단계적 도입 정책 폐기. 영상 1편이든 100편이든 동일 검색 로직.
- 임베딩 모델: 로컬 sentence-transformers/all-MiniLM-L6-v2 (384차원, CPU 100ms/쿼리, 외부 API 의존 0)

##4.5 코믹 패널 및 이펙트 연출 시스템

### 4.5.1 편집 친화 DOM 구조 (C-3, MO-5 보정 — panel 폐기, layer + split-region)
viewport
└─ scene-container (카메라 제어)
   └─ scene-group (씬 1개 = 1개 그룹)
      ├─ split-region-container         ← layout 없으면 default region 1개로 폴백
      │  └─ split-region[region_id]     ← clip-path 적용 단위 (분할 활성 씬에서만 의미)
      │     ├─ bg-layer                  data-edit-id="scene_03_default_bg"
      │     ├─ props-layer               data-edit-id="scene_03_prop_01"
      │     ├─ character-layer           data-edit-id="scene_03_character_01"
      │     ├─ data-viz-layer            data-edit-id="scene_03_dataviz"
      │     └─ foreground-layer          data-edit-id="scene_03_foreground"
      └─ scene-effects-layer             (씬 단위 만화 이펙트, region 위)

핵심 설계 원칙:
- layer = 객체 분리 + 편집기 hit-test 단위 (모든 씬에 항상 존재). 모든 시각 객체는 처음부터 독립 레이어.
- split-region = 화면 분할 컷 컨테이너 (split_diagonal 등 layout 활성 씬에만 분리, 그 외엔 default 1개 폴백).
- 두 개념 분리로 미리보기 편집기는 항상 같은 DOM 구조를 가정 가능 (분기 코드 단순화).

모든 엔진 region-aware 수정 의무:
- applyParallax → region별 추가 오프셋
- buildLipsyncTimeline → region[].character[] 순회 + data-active="true"만 (C-4)
- buildTypographyTimeline → 씬 단위(split-region-container 밖)
- spawnAmbientParticles → 씬 단위 그대로

### 4.5.2 화면 분할 레이아웃 6종 (MO-5 보정 — panels → regions)
